SECTION A - MISSION AND NON-NEGOTIABLE RULES
=========================================================================

A1. WHAT YOU ARE BUILDING
{{APP_NAME}} is {{ONE_LINE_PRODUCT_STATEMENT}}.
(Example shape: "a self-hosted VPN reseller platform where 3X-UI is the
source of truth and the app adds accounts, resellers, quotas, payments and
support chat on top".)

Target deployment: a very small server - 1 vCPU, 512 MB RAM, one SQLite
file on local disk, one Go binary serving both API and UI on one port.
This is a design requirement, not an aspiration: every feature must be
justified against that budget.

A2. THE TEN NON-NEGOTIABLE INVARIANTS
Break any of these and the build is wrong, even if it compiles.

 1. THE EXTERNAL SYSTEM IS THE SOURCE OF TRUTH.
    Every write to the external system follows: write -> fresh read back
    -> confirm -> only then write the local record. Never insert the local
    row first and hope the remote call succeeds. A provisional row may
    exist inside a transaction, but it must be rolled back if the remote
    call fails (no orphan resource, no orphan assignment, quota released).

 2. AMBIGUOUS WRITES ARE RECORDED ONCE.
    Any remote write that can time out mid-flight goes into an outbox table
    with UNIQUE(integration_id, op, idempotency_key). A background
    reconciler executes and confirms it. A retried user action can never
    create a second remote object.

 3. THE REMOTE SYSTEM WINS EVERY CONFLICT.
    Limits, expiry, enable/disable state and usage are mirrored FROM the
    remote system on every sync. The app never derives a live limit from an
    offer, a plan, or a cached value. A limit changed by hand in the remote
    panel must appear in the app on the next tick, and the app must say when
    the mirror last changed.

 4. NEVER CLAIM A REMOTE EFFECT YOU DID NOT VERIFY.
    "Suspended", "revoked", "created" are words that may only be shown
    after a verified remote response. If the call failed, the UI says the
    call failed - it does not optimistically show success.

 5. NO SSRF, NO CREDENTIAL LEAK THROUGH THE BACK DOOR.
    Outbound calls to user-supplied base URLs pass a guard: reject
    loopback, private ranges (10/8, 172.16/12, 192.168/16, 169.254/16,
    ::1, fc00::/7), link-local and cloud metadata addresses unless the
    address is explicitly allowlisted by a super admin. Redirects are not
    followed blindly. Every outbound request has a hard timeout.

 6. QUOTAS ARE COUNTED INSIDE A TRANSACTION.
    Concurrent claims/sales cannot exceed a cap. Counting happens in the
    same transaction as the insert, and a failed remote write releases the
    count. Never "check then insert" in two separate steps.

 7. SECRETS NEVER LEAVE THE SERVER.
    Remote tokens, URLs with embedded credentials, client UUIDs/passwords,
    signing keys and session keys must never appear in frontend code, in
    browser storage, in a public API response, in Git, in logs, in error
    messages, in test snapshots or in docs. Redact every error path. Sealed
    secrets live in a BLOB column (there is no plaintext column to put them
    in) and are sealed with AES-256-GCM using a 32-byte key from env.

 8. EVERY PRIVILEGED ACTION IS AUDITED.
    Actor, action, target, result, timestamp and non-secret context, in an
    append-only table. Refusals are audited as DENIED. Destructive local
    actions snapshot the row's identity (owner, remote key, plan) inside the
    delete transaction, so the audit trail never says only "id 37".

 9. DESTRUCTIVE ACTIONS ARE LOCAL AND REVERSIBLE.
    Deleting a customer's remote resource from the app is forbidden. Removal
    is local-only after a grace period with an undo. Remote deletion, if it
    ever exists, is a separate, explicit, super-admin-only, audited action.

10. THE UI IS ALLOWED TO SAY "I DON'T KNOW".
    unknown, stale, read_error, missing and disabled are five different
    facts and must render as five different states. A resource the remote
    panel no longer lists must never render as "healthy, 0% used" and must
    never match a "healthy" or "unused" filter.

A3. HOW YOU WORK WITH ME
- Language: Sinhala + English mix as described above.
- Order of work: AUDIT -> PLAN -> IMPLEMENT -> VERIFY. Confirm the real
  state of the repository before writing code. Do not assume.
- One item at a time. FIX -> BUILD -> UNIT QA -> LIVE QA -> GATE -> close
  it. Nothing advances on an unverified item.
- A feature is "done" only when UI + API authorization + DB persistence +
  failure paths + tests are all proven. The existence of a button or a
  handler proves nothing.
- Never write a claim without the command or file that proves it. Anything
  not executed is marked NOT RUN. Do not fabricate test results, screenshots
  or live API output.
- A behaviour change to a business rule needs my decision first. Record it
  as D-xxx in docs/DECISIONS.md with the reason. Never change behaviour
  silently and never "helpfully" overturn an ownership rule.
- When information is missing, ask ONE question with concrete options.
  Do not stack five assumptions.
- If a change is destructive (schema drop, data reset, production remote
  write, permission widening), stop and ask before doing it.
- End every turn with: files changed and why, commands run and their real
  output, what is verified vs not, and the next single item.

SECTION B - TECHNOLOGY STACK (LOCKED)
=========================================================================

B1. BACKEND
- Go, latest stable ({{GO_VERSION}}, e.g. 1.27).
- Standard library net/http only. No router framework, no ORM, no DI
  framework. Hand-written mux with explicit pattern matching, a middleware
  chain and a single response helper.
- SQLite through modernc.org/sqlite (pure Go, no cgo) so the binary builds
  without a C toolchain and `go test -race` is possible in CI.
- golang.org/x/crypto for argon2id.
- Total direct dependencies: 4 maximum. Adding a fifth requires a
  D-xxx entry explaining why the stdlib cannot do it.
- go.mod module path: {{MODULE_PATH}}.

B2. DATABASE
- SQLite single file at {{DATA_DIR}}/{{APP_NAME}}.db.
- Pragmas on open: journal_mode=WAL, foreign_keys=ON, busy_timeout=5000,
  synchronous=NORMAL.
- Pool: SetMaxOpenConns(4), SetMaxIdleConns(4), SetConnMaxLifetime(30m).
  SQLite serialises writes; the pool must not pretend otherwise.
- One transaction helper (WithTx) used everywhere. No naked Begin.
- Migrations: embedded via //go:embed, numbered 0001_xxx.sql upward, each
  file applied inside its own transaction, idempotent, recorded in a
  schema_migrations table. /api/ready reports the current schema_version.
- There is exactly ONE canonical database path per environment. Stale
  copies living in the repo (var/data, cmd/*/var/data, *.pre-*.db) are a
  bug, not a convenience - never create a second path.

B3. FRONTEND
- React + TypeScript (strict) + Vite.
- react-router-dom for routing, zustand for state, lucide-react for icons.
- Tailwind through @tailwindcss/vite, plus one tokens.css that is the SINGLE
  source of colours, radii, spacing, shadows and typography CSS custom
  properties. No hardcoded hex colour in any component.
- Optional heavy visuals (three.js / particles) must be lazy-loaded into a
  separate chunk and must be disabled by a Low-Resource mode.
- Linting: oxlint. Types: tsc -b. Both are gates.
- No Node.js runs on the production server. The SPA is built in CI or on the
  dev machine, embedded into the Go binary with //go:embed, and served from
  the same port as the API.

B4. DELIVERY
- One binary, one port, both UI and API. SPA fallback for client routes,
  JSON 404 for /api/*, hashed assets served with long cache headers, and
  /assets/nope.js must stay 404.
- Reverse proxy: Caddy with automatic HTTPS (config shipped in deploy/).
- Process supervision: systemd unit shipped in deploy/.
- Backup: a documented, rehearsed procedure (VACUUM INTO a timestamped
  file, plus a restore rehearsal that is actually executed once and recorded
  in the QA report).

B5. EXPLICITLY OUT OF SCOPE FOR v1 (unless the owner overrides)
{{EXTRA_OUT_OF_SCOPE}}
(Default list: Docker/Kubernetes, Redis, PostgreSQL, a job-queue server,
an SPA state library other than zustand, a chart library dependency, native
mobile apps, automated payment-gateway integration, and any remote-panel
feature that the remote API does not officially support.)

SECTION D - ACTORS, RBAC AND OWNERSHIP
=========================================================================

D1. EXACTLY THREE ACTORS
  super_admin  platform owner. Sees and may do everything.
  admin        reseller/operator. Only assigned resources, only own
               customers, only within its quota.
  client       end customer. Only their own resources.

Two separate doors:
  /staff/login   for super_admin and admin
  /login         for client
A credential from the wrong door answers 403 wrong_portal. Enforce this
server-side, on the login handler and on every authenticated route.

D2. PERMISSION MATRIX (mandatory, in docs/REQUIREMENTS.md)
Columns: action | super_admin | admin | client. Cover at minimum: create
resources, assign/sell, set prices, create/suspend staff, edit own profile,
see own history, see other customers' data, see server-wide metrics, read
audit, change global settings. Every row is enforced in the service layer,
never only by hiding a button.

D3. OWNERSHIP IS ROW-LEVEL
Every query that returns customer-owned rows is filtered by owner in SQL,
not in the handler and not in the frontend. A resource id belonging to
another owner answers 404 (not 403) so existence is not leaked.
Ownership rules must be tested with a negative test per resource type, e.g.
TestClientCannotReadAnotherOwnersResource, TestAdminCannotTouchUnassignedServer,
TestSuspendedAdminIsRefused, TestWrongPortalIsRefused.

D4. AUTH DETAILS
- Password hashing: argon2id, per-user salt, parameters documented in
  docs/ARCHITECTURE.md.
- Password policy: minimum length, entropy check, small blocklist, checked
  before hashing, with unit tests covering the rejection cases.
- Sessions: opaque 32-byte random token, stored server-side, delivered in an
  HttpOnly + SameSite=Lax + Secure cookie (Secure off only when
  {{APP}}_INSECURE_COOKIES is explicitly set for local dev). The session row
  holds user id, created, last seen, ip fingerprint, user-agent fingerprint.
  Logout deletes the row. Idle AND absolute expiry are both enforced.
- CSRF: SameOrigin check on every state-changing request, plus a required
  custom header.
- Rate limiting: per-IP and per-account on login, register, password reset
  and every mail-sending route. An in-memory token bucket is acceptable at
  this scale, but the limits and the 429 response must be tested.
- No dev auth bypass may exist in the codebase. There must be a test that
  fails if a bypass flag is ever reintroduced into the bundled output.
- Password reset / email verification: time-limited single-use token, stored
  hashed, never logged, identical response for known and unknown accounts.

INDEX RULES

E1. STATE MACHINES (write them down, test every transition)
  assignment:  PROVISIONING -> ACTIVE -> (SUSPENDED | EXPIRED | RELEASED |
               SERVER_UNAVAILABLE | REVOKED_BY_OWNER)
  order:       DRAFT -> PENDING_PAYMENT -> PAID -> FULFILLED
               (CANCELLED and REFUNDED reachable only from the documented
               states)
  integration: UNKNOWN -> ACTIVE <-> DEGRADED -> REAUTH_REQUIRED ->
               CONNECTION_UNAVAILABLE -> DISABLED
  outbox:      PENDING -> IN_FLIGHT -> DONE | FAILED_RETRYABLE | DEAD
Illegal transitions return a typed error and are unit tested. A transition
that is legal but destructive requires an explicit confirmation flag.

E2. ATOMICITY STATEMENT
A local SQLite transaction NEVER covers a remote call. Remote effects are
reconciled through the outbox plus fresh reads. State this in
docs/ARCHITECTURE.md and honour it in code.

SECTION F - BACKEND LAYOUT
=========================================================================

Dependency direction, one way only:

  cmd/{{APP}}d            process wiring: config, db, server, jobs, shutdown
    -> internal/httpapi   transport only: routing, decode, encode, status
    -> internal/domain    business rules, state machines, quota, policies
    -> internal/store     SQLite only: queries, transactions, migrations
    -> internal/remote    outbound client for the external system
  internal/config         env parsing, fail closed
  internal/auth           argon2id, sessions, RBAC, ownership, rate limit, seal
  internal/audit          append-only privileged log
  internal/jobs           sync, reconcile, purge, retention
  internal/mail           outbound mail behind an interface (optional)
  internal/integrations   integration lifecycle (add / test / disable / remove)

Enforced rules:
- httpapi holds no business rules. It decodes, validates shape, calls the
  domain, encodes. It never touches the DB driver.
- domain imports store interfaces and never httpapi; it holds every rule,
  every state machine and every quota decision.
- store is the only package that speaks SQL.
- remote is the only package that performs outbound calls.
- No import cycles. No global mutable state. Dependencies injected in cmd.
- Every package has a doc comment stating its one responsibility.
- Errors are typed sentinels or wrapped error codes mapped at the HTTP edge
  to exactly ONE envelope:
    { "error": { "code": "...", "message": "...", "details": {...} } }
  Codes are stable and machine-readable: validation, unauthorized,
  forbidden, wrong_portal, not_found, conflict, quota_exceeded,
  rate_limited, upstream_failed, upstream_timeout, internal.

STARTUP SEQUENCE (exactly this, with logs that carry no secrets)
  load config (fail closed) -> ensure data dir 0700 -> open SQLite + pragmas
  -> apply migrations -> log schema_version -> start jobs -> serve HTTP
  -> on SIGINT/SIGTERM: stop accepting, drain 10s, stop jobs, close DB.
A failure at any step exits non-zero with a logged reason. The process never
starts half-configured.

MIDDLEWARE CHAIN (order matters, document it)
  recover -> request id -> access log (no bodies, no secrets) -> realistic
  timeout -> SameOrigin/CSRF -> rate limit -> session load -> RBAC guard
  -> ownership guard -> handler.

JOBS
- sync: per integration every {{SYNC_INTERVAL}} (e.g. 60s), bounded
  concurrency, writes usage snapshots and mirrors remote limits.
- reconcile: drains the outbox, verifies ambiguous writes, marks dead
  letters after N attempts and notifies the owner.
- purge: deletes local rows whose grace period expired, snapshotting identity
  into the audit log inside the delete transaction.
- retention: trims usage snapshots and old audit rows per a documented policy.
- All jobs must be idempotent, cancellable through context, and must not run
  when the process is shutting down.

SECTION G - HTTP API CONTRACT
=========================================================================

G1. ROUTE GROUPS
  GET  /api/health                  liveness, no DB access
  GET  /api/ready                   readiness: db ping, schema_version,
                                    build sha, ui embedded yes/no
  POST /api/setup/bootstrap         one-time super admin; 409 after any user
  POST /api/auth/register|login|logout|change-password|forgot|reset
  GET  /api/me                      principal + permissions
  CRUD /api/{resource}              owner-scoped
  /api/admin/*                      staff only
  /api/me/*                         client only
  POST /api/{resource}/{id}/{action} explicit verbs for state changes
                                    (suspend, resume, release, restore, verify)

G2. CONVENTIONS
- JSON in, JSON out, explicit content types, no HTML errors on /api/*.
- Every list: filter params + pagination (limit/offset or cursor), total
  count, and explicit unknown/unread counts. Filters are also accepted by the
  UI through the URL so a refresh keeps them and a link is shareable.
- 201 + Location on create. 409 for conflicts with a specific code
  (tag_locked, quota_exceeded, already_exists). 403 vs 404 as per D3.
- Idempotency: mutating routes accept an Idempotency-Key header and reject a
  duplicate inside the window.
- Every endpoint is documented in docs/API_CONTRACT.md with method, path,
  auth, request schema, response schema, error codes and one example.
- A route test exists per endpoint: happy path plus at least one refusal.

A role hitting a route it does not own is redirected to its own home, and the

H2. DESIGN SYSTEM
- tokens.css is the single source: colours, surfaces, text, borders, radii,
  shadows, motion durations, font stacks. Every preset defines the full token
  set. ThemeProvider may override any token through inline custom properties
  for user customisation.
- Presets (minimum 3): Light, Dark, Modern, each with a small set of
  sub-themes that also define AA-contrast text colours.
- Typography must include a Sinhala-capable fallback stack
  ('Noto Sans Sinhala', 'Iskoola Pota', 'Nirmala UI').
- Components (own, no UI-kit dependency): Button, Input, Select, Checkbox,
  Switch, Tabs, Dialog (WAI-ARIA focus trap, initial focus, focus restore,
  aria-modal), Tooltip, Toast, Table (sortable, aria-sort), Pagination,
  Badge, StatusBadge, Card, MetricCard, EmptyState, Skeleton, Spinner,
  StepProgress, AsyncState, Dropdown, SavedViewsBar, SelectionBar, QrCode,
  and hand-written SVG charts (Bar, Line, Donut, Sparkline, Progress).
- Reduced motion respected globally and per component. A Low-Resource mode
  disables 3D, glass and animation, and must visibly reduce work.
- Command palette (Ctrl/Cmd+K): navigation + actions + theme groups,
  filter-as-you-type, arrow keys, Enter, Esc, aria-activedescendant.

H3. HONEST STATES - MANDATORY PER SCREEN
Every data screen implements and visibly distinguishes:
  loading (skeleton) | empty | error (with retry) | partial failure (one
  integration down, the rest still shown) | stale (with age: "synced 4 min
  ago", warning styling when stale) | unknown | missing-from-remote |
  disabled | forbidden.
A resource the remote system no longer lists renders as "missing from panel"
- never as healthy, and never inside a "healthy" filter.
Every displayed number is either measured (with its timestamp) or explicitly
labelled as an estimate. No fake charts, no demo series on production paths.

H4. PRODUCT RULES TO RENDER IN THE UI
{{LIST_YOUR_PRODUCT_RULES}}
Shape reference (these are Veylix's; replace them with yours):
- 3 concurrent FREE resources per client, 5 per rolling 30 days, per server;
  counting comes from a ledger, never from scanning rows.
- A visibility tag locks once the resource is issued; changing it is refused
  with 409 tag_locked and audited.
- Release is local-only with a 3-day grace and an undo; the remote object is
  untouched. Restore is available to the owner and to an operator.
- Only the owner may release their own resource. An operator acting on a
  customer's behalf is refused ON PURPOSE (ownership rule) unless the super
  admin escalates with an audited, explicit action.

SECTION L - DELIVERY: INSTALL, UPGRADE, BACKUP
=========================================================================
L1. INSTALLER (one command, idempotent)
- Validates inputs and refuses to overwrite an existing data dir without
  --force.
- Creates a dedicated system user, the directory layout and a 0700 secrets
  dir.
- Generates the encryption and session keys if absent and prints where they
  are (never the values in a log).
- Installs the systemd unit, enables and starts it, waits for /api/ready.
- Configures Caddy with the given domain and waits for the certificate.
- On any failure prints exactly what failed and how to roll back. It never
  leaves a half-installed state.
- Prints the URL and the first-run bootstrap instruction.

L2. UPGRADE
- Stops the service, backs up the DB, replaces the binary, runs migrations,
  waits for /api/ready, restarts jobs. A failed migration aborts and restores
  the previous binary. The procedure is documented and rehearsed once.

L3. BACKUP / RESTORE
- A script producing a timestamped consistent DB copy (VACUUM INTO) plus a
  reference to the secrets file, with retention.
- A documented restore rehearsal that was actually executed; the output goes
  in the QA report. "Backups work" is not a claim without a restore.

L4. CI
- ci.yml: build, vet, gofmt, test, race, frontend types, lint, build, audit,
  docs:verify on every push.
- release.yml: build the SPA, embed it, build the binary, run the package
  proof, publish the artefact with a checksum.

SECTION O - THINGS I EXPECT YOU TO GET RIGHT (hard-won lessons)
=========================================================================
 1. Write the refusal test before the feature test. Most real bugs are a
    missing refusal.
 2. For every fix, prove the test fails when the fix is reverted. A test that
    passes both ways proves nothing.
 3. Never leave an unread/unknown state implicit. If a value could not be
    read, say so with a flag, a reason and a timestamp.
 4. Do not let the docs grow faster than the code. Eight documents, each with
    one question it answers.
 5. Do not keep stale artefacts (old DBs, old binaries, diagnostic dumps) in
    the repo. They become the source of wrong diagnoses.
 6. Do not optimistically render a remote action as successful.
 7. Do not delete a customer's remote resource from the app, ever.
 8. Do not widen a permission to make a button "work". Ask the owner first.
 9. Prefer an explicit, boring implementation over a clever abstraction.
10. When a live test is blocked (no VM, no live remote, no mail server), write
    it down as BLOCKED with the reason instead of pretending it ran.
